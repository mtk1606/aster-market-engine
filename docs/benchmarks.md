# Benchmarks

These are early measurements, not exchange-production performance numbers. Both workloads were generated by the repository's benchmark scripts and keep very few orders live at a time. Results from a different machine are not directly comparable.

## First synthetic replay baseline — October 9, 2026

| Setting | Value |
| --- | --- |
| Workload | `synthetic-serial-churn-v1` |
| Size | 100,000 order lifecycles / 500,000 records / 15,400,000 bytes |
| Compiler | GCC 14.2.0, C++20, CMake Release build |
| Machine | Virtualized AMD EPYC 9V74, Linux x86-64 |
| Repetitions | 1 warmup + 5 measured, fresh process per run |
| Median | 14,512,867 frames/s |
| Range | 13,988,044 to 17,037,129 frames/s |
| Final state | 0 orders; digest `cbf29ce484222325` |

To repeat that experiment:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure
python3 tools/benchmark.py build/aster-replay --orders 100000 --repetitions 5
```

## Comparing the two readers

A later run used exactly the same 500,000-record file with `mmap` and `read()` at a 65,536-byte chunk size. The host exposed five virtual CPUs. Each path had an excluded warmup and five measured process runs; mode order was alternated. The input SHA-256 was:

`b8b0a697d0361b0899a197dae9f671afa759c342c6a9bbbfb39d1c121abdc588`

| Input path | Median frames/s | Slowest run | Fastest run |
| --- | ---: | ---: | ---: |
| `mmap` | 15,499,986 | 14,558,013 | 17,540,814 |
| `read()` | 15,850,366 | 7,009,875 | 17,130,731 |

Every run reported the same 500,000 frames, 15,400,000 input bytes, 500,000 applied events, zero remaining orders and digest `cbf29ce484222325`.

```bash
python3 tools/compare_io.py build/aster-replay --orders 100000 --repetitions 5 --chunk 65536
```

The lowest `read()` sample is a reminder not to pick a winner from a handful of measurements on a shared machine. There is no convincing speed difference here. These tests exercise warm-cache replay of a synthetic, small-book workload. They do not measure p99 latency, realistic full-depth book pressure, cold storage I/O or QSE-relative performance.

The next useful experiment is a real-session replay with representative resting depth, plus breakdowns of decoding, framing and book updates. Local unit tests, seeded differential sequences and sanitizer builds were run before recording this baseline; the status of hosted CI must be checked independently.
